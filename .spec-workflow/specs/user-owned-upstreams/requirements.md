# Requirements Document

## Introduction

用户自主添加和管理上游地址、凭据及模型，不再依赖管理员统一导入上游模型。上游和模型属于添加它们的用户；调用时必须严格限定到对应上游，不因模型名称相同、重试或内部辅助任务而切换到其他用户或其他上游。

本文件记录最新需求，并替代此前“管理员为用户绑定共享上游”的实现方向。当前工作区已有未完成的后端归属字段和路由隔离改动，尚不能视为可用功能。

## Alignment with Product Vision

项目未提供 steering/product.md。本功能沿用已有渠道、会话、设置及加密凭据模块，使用户在自己的账户内完成上游配置和模型调用，不增加共享凭据或共享模型配置的依赖。

## Requirements

### Requirement 1 — 用户管理自己的上游

**User Story:** 作为用户，我希望自主添加、查看、修改、停用和删除自己的上游，以便不依赖后台配置即可调用自己的服务商。

#### Acceptance Criteria

1. WHEN 已登录用户添加上游 THEN 系统 SHALL 从认证上下文确定所有者，不接受客户端指定所有者。
2. WHEN 用户查询上游 THEN 系统 SHALL 仅返回该用户拥有的上游，并仅返回脱敏后的凭据。
3. WHEN 用户修改、删除、发现模型或管理模型 THEN 系统 SHALL 在服务层检查上游所有权。
4. IF 上游属于其他用户或属于旧的管理员共享配置 THEN 用户管理接口 SHALL 返回资源不存在，且不得发起上游网络请求。
5. WHEN 用户保存上游凭据 THEN 系统 SHALL 使用已有数据加密机制保存，并允许修改其他配置时保留原凭据。

### Requirement 2 — 用户自主维护模型目录

**User Story:** 作为用户，我希望发现或手动添加自己上游的模型，以便后台不再统一添加上游模型。

#### Acceptance Criteria

1. WHEN 用户添加上游 THEN 系统 SHALL 提供远端模型发现及手动添加模型的入口。
2. WHEN 用户添加上游模型 THEN 系统 SHALL 创建属于该用户的模型身份及仅指向该上游的路由。
3. IF 同一用户的不同上游或不同用户的上游包含相同模型名称 THEN 系统 SHALL 为每个上游模型提供不同的稳定调用标识。
4. WHEN 前端展示模型 THEN 系统 SHALL 显示真实模型名称及可区分的上游名称，而非仅展示内部调用标识。
5. WHEN 用户删除上游或其模型 THEN 系统 SHALL 清理相应私有路由和模型身份，不影响其他用户或其他上游。
6. WHEN 用户查询可用模型 THEN 系统 SHALL 仅展示自己拥有且实际可路由的模型；不得通过共享目录缓存泄露其他用户的模型。

### Requirement 3 — 全调用路径严格隔离

**User Story:** 作为用户，我希望指定模型始终使用对应上游，以免相同名称的模型导致凭据、数据或调用费用串到其他上游。

#### Acceptance Criteria

1. WHEN 系统解析私有模型路由 THEN 系统 SHALL 同时校验请求用户、模型所有者和上游所有者，并限定到该模型绑定的上游。
2. WHEN 用户直接提交其他用户的模型调用标识 THEN 系统 SHALL 拒绝调用，且不得发送上游请求。
3. WHEN 上游失败、熔断、限流或路由重试 THEN 系统 SHALL 不回退到其他上游的同名模型或旧的共享模型。
4. WHEN 会话、临时会话、图片、视频、标题生成或上下文压缩调用用户模型 THEN 系统 SHALL 传递相同用户身份并应用同样的所有权校验。
5. IF 内部调用缺少用户身份 THEN 系统 SHALL 不调用任何用户私有模型。

### Requirement 4 — 安全、计量和迁移

**User Story:** 作为平台运营者，我希望用户配置不会使服务器访问内网或泄露凭据，并保持现有数据迁移可控。

#### Acceptance Criteria

1. WHEN 用户配置地址或系统访问用户上游 THEN 系统 SHALL 拒绝服务器回环、私网、链路本地和元数据地址，并对 DNS 解析及 HTTP 重定向执行同样的检查。
2. WHEN 用户管理上游及模型 THEN 系统 SHALL 限制输入长度、上游数量、模型导入数量及请求超时，并不开放管理员级路由配置。
3. WHEN 调用用户自己的上游模型 THEN 系统 SHALL 保留用量记录，但不要求管理员维护平台价格或预充值平台余额；上游服务商费用仍由用户自行承担。
4. WHEN 升级既有数据库 THEN 系统 SHALL 将旧记录明确识别为管理员共享配置，不自动将其归属或公开给任意用户，不删除旧数据。
5. WHEN 迁移旧后台管理入口 THEN 系统 SHALL 不再将管理员统一添加上游模型作为用户使用模型的必要步骤。旧配置的保留和内部系统用途须明确说明，不得作为私有模型的调用回退。

### Requirement 5 — GitHub Actions 验证

**User Story:** 作为维护者，我希望安装依赖、编译和测试仅在 GitHub Actions 执行，而不是在本地环境执行。

#### Acceptance Criteria

1. WHEN 继续实现该功能 THEN 开发流程 SHALL 不在本地安装任何软件或依赖，不执行本地编译。
2. WHEN GitHub Actions CI 运行 THEN CI SHALL 检查 Go 格式及静态规则、构建默认及 sidecar 标签组合、执行后端测试。
3. WHEN GitHub Actions CI 运行 THEN CI SHALL 执行前端类型、架构、API 契约检查及前端构建。
4. WHEN 提交功能测试 THEN 测试 SHALL 覆盖跨用户访问拒绝、同名模型隔离、重试不串上游、凭据脱敏及私有地址拦截。
5. IF 尚未推送或触发远端 Actions THEN 交付说明 SHALL 明确 CI 尚未运行，不声称验证通过。

## Non-Functional Requirements

### Code Architecture and Modularity
- 保持 domain → application → repository → infra/transport 分层。
- 前端页面保持薄入口，业务组件和 hooks 位于 settings feature，网络调用位于 shared/api。
- 复用现有凭据加密、渠道调用及设置组件，不新增独立的重复调用栈。

### Performance
- 私有目录按所有者查询，不使用可混淆用户身份的共享缓存。
- 模型发现及批量添加有数量和时间限制，避免无限响应或无限导入。

### Security
- 所有权校验必须位于服务层，不能依赖隐藏前端按钮。
- 用户上游使用严格出站策略，不能继承管理员上游的私网信任授权。
- 密钥不得出现在普通响应、浏览器持久化存储或日志中。

### Reliability
- 上游模型及路由创建、删除保持事务一致性。
- 稳定调用标识不因上游展示名称修改而改变。
- 测试和编译交由现有 GitHub Actions CI；不得将未执行的验证报告为通过。

### Usability
- 在用户设置中提供上游管理入口及中英文文案。
- 同名模型明确展示对应上游，删除操作有确认，空目录提供添加引导。
- 错误信息说明配置或远端请求失败，不泄露其他用户资源信息。
